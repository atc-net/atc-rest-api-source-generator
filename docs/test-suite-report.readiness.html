Atc REST 3.0 readiness

State of feature/error-body-3.0 (generator) and feature/error-body-backlog (minimalapi), 5 October 2026. Atc.Rest.Client 2.1.0 is released on nuget.org and the generator now uses the package. Nothing else is released or pushed; the generator still uses minimalapi through a temporary project reference.

The numbers on this page come from the run that wrote it: the verdicts per matrix on the Overview tab, the compile gate and the diagnostics on Feature support, and the Showcase apps under Playwright. The commit the run was made from is in the page header. These notes are written by hand, so they carry no counts - a test checks that, so editing this page alone can turn a run red. A Playwright run that started before that commit is marked stale rather than shown as this commit's. MinimalApi is tested in its own repository, unit tests and Aspire/Playwright E2E, 0 failed on 28 September.

2The validation 400 against a declared 400 body. The ValidationFilter always answers an invalid request with a ValidationProblemDetails, even where the specification declares its own 400 body. done
  • A declared ProblemDetails 400 is read as the ValidationProblemDetails subtype. The generated ValidationProblemDetails now derives from ProblemDetails, so the field errors stay typed. Those matrix cells flipped from lossy to pass.
  • A declared model or string 400 keeps its type, and the field errors are only in Content. Documented.
3Atc.Rest.Client drops non-text error bodies. MessageResponseBuilder keeps a body as bytes when the media type is neither JSON nor text, so Content is empty. released in 2.1.0 Fixed from atc-rest-client/issues/0001-error-body-kept-as-bytes-for-non-text-media-types.md and released as Atc.Rest.Client 2.1.0 on nuget.org: an error body of any media type is now read as text. The test project, every sample client and the Showcase client apps now reference the 2.1.0 package (the temporary project references are gone), and the guard test AtcRestClient_ReadsAnErrorBodyOfAnyMediaTypeAsText passes on it. The matrix did not change when the fix arrived, because the generated 3.0 client already works around the bug with every Atc.Rest.Client version. So the fix is a benefit for hand-written callers.
2.1.0 also carries atc-rest-client/issues/0002: binary responses keep an error's content type and headers, read filename*, and give a typed ErrorContentObject. The generated streamed download (x-return-stream) registers its error types, so that object is the declared error.

Fixed in this round (all in 3.0, nothing deferred)

  • Every status below 400 (found by extending the matrix to every HttpStatusCode). v2 answered every status except 200/201/202/204 with a ProblemDetails of that status: a 301 without Location, a 304 with a body, a 205 that hung, a 206 that could not send its model. Now:
    • 2xx and 300 write their declared body;
    • 205 and 304 write none;
    • the redirects take the location and write Location (a generated LocationHttpResult for 303, which ASP.NET Core has no result for);
    • a 1xx gets no factory and the new warning ATC_API_OPR030;
    • the C# client never reads a 3xx as an error;
    • TypeScript gains the arms notModified and redirection, and 205 is noContent;
    • the TypedClient returns the body of a 202-only (or 203/206/…) operation;
    • status names use the RFC names (307 TemporaryRedirect, not RedirectKeepVerb).
  • TypeScript naming. A naming strategy that differs from the API's casing renames the wire too: responses, request bodies, error bodies, stream items, SignalR payloads and MSW mocks (helpers/wireNames.ts). v2 read undefined for every renamed property.
  • TypeScript, other former 3.1 items.
    • Typed default arms.
    • An options parameter on React Query infinite hooks.
    • Unique query-key names.
    • A streamed operation sends its own method and body.
    • globalThis.Error when a spec model is named Error.
    • Cookie and querystring names under every naming strategy.
  • C# string error accessors. A declared string or text, or PlainText / PlainTextOnly, gives an application/problem+json body's message (detail, else title) instead of the ProblemDetails' JSON text. The client splits by media type.
  • C# non-text error bodies. application/xml and application/octet-stream error bodies now reach Content and the typed accessors (decoded by the Content-Type charset). They used to be lost; a body without a Content-Type was already read as text.
  • C# declared error models. The accessor no longer throws for a body of another shape (a proxy's page, another API's error). It fills the shared properties, as the custom model does.
  • C# TypedClient, Result style, downloads. The error body is now in Content; it used to be empty.
  • C# custom error model.
    • It gets its own namespace when its name collides with a spec schema (the Monta ErrorResponse).
    • It reads a body leniently, for example a numeric status into a string property, instead of throwing.
  • TypeScript error bodies. One rule for Fetch and Axios, and for success and error bodies:
    • JSON is parsed.
    • Text (text/*, application/xml, +xml) stays a string.
    • Anything else is undefined.
    Before this, Axios kept binary bodies as strings and parsed a JSON-string error twice ("42" became the number 42), and Fetch dropped XML.
  • Server. Model properties are written under their exact spec names (user_name, UserId, HTTPStatus).
  • Server string enums. A string enum is a string on the wire in every host: the generated enum carries its own JsonStringEnumConverter. Before, a host without a registered converter wrote numbers.
  • Extensible client enums. The C# and TypeScript clients read a value the specification does not list instead of failing: a C# readonly record struct with the known values, a TypeScript open union. The two feature-matrix cells that failed on an unknown value pass; extensibleEnums: false keeps the classic enum. The matrix runs that client too: its cell passes when the classic enum refuses the unknown value, which is what the option documents.
  • OpenAPI Overlays. A marker lists overlay files (Overlay 1.0 to 1.2, RFC 9535 JSONPath) that the build applies to the specification before it validates and generates; the CLI applies them too (spec overlay apply, --overlay).
  • Axios uploads. The Axios client names a FormData body multipart/form-data itself: on its fetch adapter in Node, axios labelled it form-urlencoded and the server answered 415 (the last known failure of the matrices). A Showcase spec proves the browser still sends it with its boundary.
  • Hints for the lossy cells. ATC_API_SRV002 (information) notes a 400 declared as a string while the ValidationFilter is on, and an error factory whose status declares a model says in its remarks what a call without the model writes. Both kinds of cell stay lossy; the remaining options are design decisions (see the design review).
  • A broken specification is reported, never a crash. A fuzz test (every scenario, mutated from a fixed seed, through the server, handler and client generators) found crashes that are now diagnostics: JSON text with an escaped emoji (SharpYaml; it is read as JSON now), an unknown openapi version and an empty $ref (the parser's reason is reported), a value of another kind where an object belongs (ATC_API_VAL001 naming the place), a prefixItems keyword that is no string, and a handler scaffold that cannot be written (ATC_API_GEN019).
  • Showcase. Since the generated endpoints enforce scopes, the demo user had none and the scoped operations answered 403; with Playwright in this report it showed at once. The demo user now holds the oauth2 scopes.

Known limitations (documented)

  • The C# EndpointPerOperation client has no result class for streamed item operations (SSE, JSON Lines) or for a streamed download (x-return-stream, which returns StreamBinaryEndpointResponse with a typed ErrorContentObject), so they get no IsDefaultError. A buffered file download does have a result class, with typed errors.
  • HttpClient.Timeout (100 s) caps long per-operation retry timeouts.
  • The build finds multi-part specs by the {Base}_{Part}.yaml convention only.
  • Node's fetch rejects every 407 response, so the Fetch client cannot be observed on 407 in Node. Browsers behave differently; this is a platform limit, not a client one.
  • Not exercised by the matrix: the How it was tested tab lists everything the E2E run does not cover (secured and rate-limited operations, the Development environment, browser runtime, …).

Error Body Matrix

What the generated server writes for every HTTP status (every System.Net.HttpStatusCode value, plus 418, 425, 499 and 599) and every way a specification can declare it, and what each generated client makes of those bytes. Every cell is a recorded result of a real run: the generated server on Kestrel, each generated client calling it over HTTP.

Verdicts

passThe client exposes what the documented contract says: the right status, accessor, type and arm, every field of the body as on the wire, no exception.
lossyThe client does what the documentation says and does not throw, but the typed value cannot hold some fields of the body - the cell names them; they stay in the raw body (Content). E.g. the custom error model reading a ProblemDetails, or a string accessor reading a validation 400. The badge next to it says what was lost; its colour is our suggested assessment (see Design review below): good by design design iteration fix.
failThe contract is broken: a wrong status, accessor, type, arm or field value, or an exception.
platformOutside the generated code: the runtime itself refuses the response (reproduced with a plain call).
naNot applicable: a 1xx status is never a final response (RFC 9110 §15.2), so no factory, accessor or arm exists - the server row checks that none is generated.

Reading the axes

The server has one mode: it writes what the specification declares. TypedClient and EndpointPerOperation are generation modes of the C# client, and errorResponseFormat is read by the C# EndpointPerOperation client only - it decides how a status with nothing declared is read. The TypeScript clients have one mode. So the matrix is one server against eight clients, per declaration style and status.

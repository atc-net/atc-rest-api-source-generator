# Samples

Every C# project here is generated at build time by the source generator from the specification in its folder; no CLI step is needed. Build the solution once (`dotnet build Atc.Rest.Api.SourceGenerator.slnx`) and the generated code is there. The only exception is the TypeScript client of the two Showcase React apps, which the CLI produces (`--client-type Fetch` or `Axios`).

Two host wiring styles appear below:

- **Plain**: the generated `MapEndpoints()` only, with `AddProblemDetails()`, `UseExceptionHandler()` (outside Development) and `UseStatusCodePages()` for RFC 9457 error bodies, the way the CLI's `generate server` template wires a host. No extra package - and so no request validation and no exception → status mapping (the test-suite report's *MapEndpoints host* tabs show what that costs).
- **Atc.Rest.MinimalApi**: the marker file sets `useMinimalApiPackage`, so the generator emits `Add{Name}Api()` / `Map{Name}Api()` that also register the validation filter, the global error handler and rate limiting from the specification.

Every host that authenticates does so in **demo mode**: any bearer token (and, for PetStoreFull, any `api_key` header) is accepted and a demo identity carrying the scopes or roles the specification names answers for it. See the `ServiceCollectionExtensions.cs` of the host. None of it is for production.

## Clients for third-party specifications

These samples hold no server. They generate a client from a published third-party specification (checked in next to the marker file) and show how a consumer wires and tests it. The `*-App` projects are console applications that call the live API with a bearer token (see their `BearerTokenProvider.cs`); the `*.Tests` projects run without network access.

| Sample | Demonstrates | Generation mode | Runnable |
|--------|--------------|-----------------|----------|
| [ThirdParty-EPO-Clients/Eloverblik.ThirdPartyApi.Client](ThirdParty-EPO-Clients/Eloverblik.ThirdPartyApi.Client) | One endpoint class per operation, an overlay (`api-1.overlay.yaml`) applied on top of the published spec, a named `HttpClient` | `EndpointPerOperation` | `EloverblikThirdPartyApiClient-App` (console); `Eloverblik.ThirdPartyApi.Client.Tests` (`dotnet test`, see its [README](ThirdParty-EPO-Clients/Eloverblik.ThirdPartyApi.Client.Tests/README.md)) |
| [ThirdParty-EPO-Clients/EloverblikCustomerApiClient](ThirdParty-EPO-Clients/EloverblikCustomerApiClient) | The same mode on a second specification sharing the `Eloverblik-ApiClient` HTTP client name | `EndpointPerOperation` | Library only |
| [ThirdParty-EPO-Clients/MontaClient](ThirdParty-EPO-Clients/MontaClient) | A custom error response model (`customErrorResponseModel`), generated OAuth token management, partial models to extend generated records, an overlay | `EndpointPerOperation` | Library only (DI wiring in its [README](ThirdParty-EPO-Clients/MontaClient/README.md)) |
| [ThirdParty-Typed-Clients/Eloverblik.ThirdPartyApi.Client](ThirdParty-Typed-Clients/Eloverblik.ThirdPartyApi.Client) | One typed client for the whole spec (`clientGranularity: Single`, explicit `clientName`), the namespace resolved from `info.title` because the spec file name is not an identifier | `TypedClient` | `EloverblikThirdPartyApiClient-App` (console); `Eloverblik.ThirdPartyApi.Client.Tests` (`dotnet test`, see its [README](ThirdParty-Typed-Clients/Eloverblik.ThirdPartyApi.Client.Tests/README.md)) |
